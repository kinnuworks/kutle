# Device firmware (ESP32-S3)

The board next to the battery's fuel gauge. It holds the device's two keys,
hashes readings itself and signs reading batches and proofs of possession. The
protocol and data formats are in `../SPEC.md`.

## Layout

| Path | What |
|---|---|
| `src/main.cpp` | Hardware layer: USB CDC serial, NVS (Preferences), hardware RNG, SMBus to the gauge |
| `lib/kutle_core/` | Keccak-256, reading encodings, Merkle tree, digests, hex. Pure C, no dependencies |
| `lib/kutle_device/` | Key derivation, signing, seed export, the line protocol. Platform-neutral behind a small HAL |
| `lib/mldsa-native/` | Submodule, pq-code-package/mldsa-native v2.0.0, ML-DSA-44 |
| `lib/secp256k1/` | Submodule, bitcoin-core/secp256k1 v0.7.1, with the recovery and ECDH modules |
| `lib/mldsa_port/`, `lib/secp256k1_port/` | PlatformIO manifests that compile the submodules unchanged |
| `include/kutle_mldsa_config.h` | mldsa-native configuration (ML-DSA-44, own namespace, reduced RAM on the board) |
| `test/test_vectors/` | Native test against `../test-vectors.json` |
| `sim/` | Host build of the same protocol code over stdin/stdout, used by the gateway tests and the end-to-end run |

secp256k1: the brief suggested micro-ecc or trezor-crypto. micro-ecc does not
return the recovery id, which Ethereum's 65-byte `r || s || v` signatures need,
and the standalone trezor-crypto repository is archived with a notice not to
use its contents (the code now lives in the trezor-firmware monorepo).
libsecp256k1 gives recoverable RFC 6979 signatures with low s, constant-time
signing and ECDH, and is the most widely reviewed secp256k1 code there is. With
RFC 6979 on both sides the firmware's ECDSA signatures are byte-identical to
viem's, which the native test checks.

## Build and test

```
python3.12 -m venv ../.venv && ../.venv/bin/pip install platformio
git submodule update --init device/firmware/lib/mldsa-native device/firmware/lib/secp256k1   # from the repo root

../.venv/bin/pio run -e esp32-s3-devkitc-1          # host-fed image
../.venv/bin/pio run -e esp32-s3-devkitc-1-smbus    # reads a bq gauge over SMBus
../.venv/bin/pio test -e native                     # vectors, on this computer
make -C sim                                         # host build for the gateway tests
```

Current build (espressif32 6.10.0, Arduino core 2.0.x): static RAM 53,864 bytes
of 327,680; flash 332,189 bytes of a 3.2 MB app partition (8 MB module).

The native test checks, against vectors generated by the TypeScript gateway:
Keccak-256, the wire and ABI encodings and leaf of seven readings (including
extreme values and negative current and temperature), Merkle roots and every
proof for trees of 1 to 7 leaves, both batch digests and both pop digests
(one of them taken from `contracts/test/fixtures/mldsa.json`), KeyGen from a
fixed seed producing the same 1,312-byte key as noble, the address and
commitment, ECDSA signatures equal to viem's byte for byte, ML-DSA signatures
verifying in both directions, and the seed wrap.

Flashing is not done yet (no board attached):
`../.venv/bin/pio run -e esp32-s3-devkitc-1 -t upload`, then
`KUTLE_DEVICE=/dev/cu.usbmodemXXXX node ../provision/src/cli.ts inspect`.

## Modes

`host-fed` (default image): the gateway sends raw readings with `BATCH` and `R`
lines. The device decodes each one, recomputes its leaf, builds the tree,
derives `fromTs`, `toTs` and `count`, computes the digest and signs. The host
never sends a leaf, a root or a digest. The device still has to believe the
values it is sent; it only guarantees that what it signs is exactly those
values.

`smbus`: the device reads the gauge itself at a fixed interval
(`KUTLE_SAMPLE_INTERVAL_MS`, default 60 s) once the gateway has set its clock
with `TIME`, buffers up to 256 readings and signs its own buffer with
`OWNBATCH`. Wiring: SDA on GPIO 8, SCL on GPIO 9, 100 kHz, gauge at the SBS
address 0x0B, with pull-ups to 3.3 V on the device side (check the pack's SMBus
levels; add a level shifter if the pack pulls up to 5 V). Standard SBS commands
used: 0x08 Temperature, 0x09 Voltage, 0x0A Current, 0x0D RelativeStateOfCharge,
0x10 FullChargeCapacity, 0x17 CycleCount, 0x18 DesignCapacity, 0x3F/0x3E/0x3D
cell 1/2/3 voltage. Per-cell Qmax and resistance have no standard SBS command.
Qmax can be read through ManufacturerBlockAccess (0x44) by building with
`-DKUTLE_BQ_MAC_QMAX=<subcommand>` once the subcommand is confirmed against the
bq40z651 technical reference manual; without it, and for WeightedRa, those
fields are 0 in smbus mode.

Both modes keep a replay guard per (chainId, ReadingLog, deviceId) in NVS: a
batch with a lower `seq` than one already signed is refused, and so is a later
`seq` whose window starts before the last signed `toTs`. Retrying the same `seq`
is allowed.

## Keys and storage

On first boot the device draws `ecdsa` (redrawn until it is a valid scalar) and
`xi` from the hardware RNG and stores both in NVS namespace `kutle`. The RNG is
read with the bootloader entropy source enabled, because with Wi-Fi and
Bluetooth off `esp_fill_random` is only a true RNG while that source is on
(ESP-IDF API reference, "Random Number Generation"). The ML-DSA key pair is
re-derived from `xi` at every boot with FIPS 204 Algorithm 6
(`keypair_internal`); the 2,560-byte secret key exists only in RAM.

Required before production, none of which is enabled in this development
image:

- flash encryption (release mode) so the NVS partition and the image cannot be
  read out of the external flash;
- NVS encryption with an `nvs_keys` partition protected by flash encryption,
  or the HMAC-based NVS key scheme on the S3;
- Secure Boot v2 so only signed images run;
- JTAG disabled by eFuse, and the USB-Serial-JTAG peripheral's JTAG function
  with it; the CDC serial port stays for the protocol.

The `LOCK` command (sent by the provisioning station after registration) makes
the device refuse to export its seed again. It is a one-way NVS flag; with
flash encryption on, clearing it means erasing the keys too.

## Signing time and memory

Measured on the host build (`BENCH 3` through `sim/`, Apple silicon): 177 us
per ML-DSA-44 signature. This only shows the code path works; it says nothing
about the ESP32-S3.

Expected on the ESP32-S3 at 240 MHz, not yet measured: roughly 20 to 60 ms per
ML-DSA-44 signature with the portable C code. The reasoning: the signing loop
repeats 4.25 times on average for ML-DSA-44 (CRYSTALS-Dilithium specification
v3.1, Table 2), every iteration is dominated by NTTs over 32-bit coefficients
and SHAKE, and the Xtensa LX7 is a single-issue core with 32 x 32 bit multiply
instructions, so a portable implementation needs a few million cycles per
signature; `MLD_CONFIG_REDUCE_RAM`, which this image enables, recomputes the
matrix instead of keeping it and costs more on top. Signing is rejection
sampled, so individual signatures vary by several times the mean. KeyGen at boot
costs about one signing iteration. secp256k1 signing is a small fraction of the
total. Replace this estimate with the output of `BENCH 20` once the board is
attached; the reply also reports the loop task's free stack.

Memory, from `mldsa/mldsa_native.h` in the pinned submodule
(`MLD_TOTAL_ALLOC_44_*`): signing allocates 44,704 bytes of working memory
without `MLD_CONFIG_REDUCE_RAM` and 13,120 bytes with it; KeyGen 26,912 and
11,584 bytes. These are stack allocations unless a custom allocator is
configured, and the header notes that some stack use remains beyond them. The
Arduino loop task is therefore given 64 KB (`SET_LOOP_TASK_STACK_SIZE`) instead
of the default 8 KB. The protocol keeps its large buffers static: the open
batch's leaves (256 x 32 bytes), the smbus reading buffer (256 readings), the
expanded secret key and the reply line, which together account for most of the
53,864 bytes of static RAM in the build above.
